1.스케줄을 저장하면 얼마 만에, 어떤 과정으로 반영되나

서버가 기기를 호출하는 푸시 채널은 여전히 없다. 대신 이미 2분마다 오가는 하트비트에 “편성이 바뀌었다”는 신호(편성 epoch)를 실어 보내고, 기기가 그것을 보고 스스로 앞당겨 조회한다.

1.1전체 흐름

  1. 관리자가 스케줄 저장즉시
    backend 모델 훅이 편성 epoch 를 +1
  2. 기기의 다음 하트비트 (2분 주기)0 ~ 120초 · 평균 60초
    응답: { "scheduleEpoch": 1785063422 }
  3. 플레이어: “내가 아는 값과 다르다” → 지터 대기0 ~ 15초
    전 기기가 한 초에 몰리는 것을 막는 분산
  4. 스케줄 즉시 재조회< 1초
    GET /schedule/:deviceId → scheduleVersion 이 달라짐 → 적용 시작
  5. 캐시 동기화신규 파일 없으면 < 1초
    신규 파일이 있으면 지터 0~1분 + 다운로드 시간
  6. 재생 중인 광고가 끝날 때 목록 교체0 ~ 현재 광고 길이
    중간에 끊지 않는다
  7. 새 편성 송출 시작

1.2소요 시간

구간시간
①→④ 새 편성 수신최대 2분 15초 (평균 약 1분)
⑤ 캐시 동기화신규 파일 없으면 1초 미만 · 있으면 지터 0~1분 + 다운로드
⑥ 화면 전환까지현재 광고 잔여 재생시간 (표준 60초 광고면 최대 +60초)
합계 (신규 파일 없을 때)최대 약 3분 15초 · 평균 약 1분 30초
★⑥ 은 지연이 아니라 의도된 동작이다

재생 중인 광고를 중간에 끊으면 그 회차의 재생로그가 남지 않아 광고주 정산 근거가 사라진다. (v1.2.1 까지는 실제로 끊고 있었고, 그것이 결함 D 였다.)

1.3폴백 — 신호를 못 받아도 반영은 된다

상황동작
하트비트 실패(일시 단절)다음 하트비트에서 재시도. 마지막 epoch 를 잃지 않아 오검출도 없음
기기가 구버전 플레이어epoch 를 읽지 않음 → 종전대로 5분 폴링으로 반영 (하위 호환)
backend 재기동epoch 가 새로 출발 → 각 기기가 스케줄을 1회 더 조회할 뿐 (놓치는 쪽이 아니라 확인하는 쪽으로 틀림)
서버 완전 단절마지막 편성을 localStorage 에서 읽어 오프라인 계속 재생

1.4시각 도래에 의한 전환은 여전히 최대 5분

⚠epoch 는 관리자 조작만 앞당긴다

편성 epoch 는 관리자 조작을 앞당길 뿐 시각 경과를 앞당기지 않는다.

예: TIME_START=09:00 편성은 09:00 정각이 아니라 09:00 ~ 09:05 사이 폴링에서 시작된다.

플레이어는 편성 규칙(기간·요일·시간대)을 갖고 있지 않고 “지금 이 순간의 결과”만 받기 때문이다(§2). 분 단위 정확도가 필요한 편성이 생기면 별도 설계가 필요하다.

2.기기당 트래픽 — 서버가 스케줄을 관리하는 비용

플레이어는 편성 규칙을 갖지 않고, 서버가 요청 시점 기준으로 합성한 평면 항목 배열 1개만 받는다. 그 대신 주기적으로 물어봐야 하므로 다음 트래픽이 발생한다.

2.3콘텐츠 다운로드는 별도이며 이것이 압도적이다

위 수치는 제어 트래픽만이다. 광고 영상은 편성이 바뀌어 새 파일이 생길 때 1회만 내려받고, 이후 재생은 로컬 디스크에서 한다(서버 트래픽 0).

★관리 대상은 폴링이 아니라 콘텐츠 교체 빈도

영상 1편(예: 80 MB)을 새로 받으면, 그 한 번이 제어 트래픽 20일치에 해당한다. 즉 대역폭 관점에서 실제로 관리해야 할 것은 폴링이 아니라 콘텐츠 교체 빈도다.

2.4참고 — 절감 여지 (현재는 조치 안 함)

  • 헤더가 본문보다 크다: 하트비트 왕복 1,441 B 중 실제 데이터는 207 B(14%)이고 나머지는 HTTP 헤더다. helmet 의 CSP 헤더(약 250 B)가 API 응답에도 그대로 붙는다.
  • gzip 미적용: 플레이어는 Accept-Encoding: gzip 을 보내지만 backend 에 압축 미들웨어가 없다. 스케줄 응답(1.6 KB, JSON)은 압축 시 60~70% 줄어든다.
  • 현재 규모에서 절감액이 무의미해 조치하지 않았다. 기기 수백 대 또는 종량제 회선에서만 검토 대상이다.

3.스케줄이 여러 개일 때의 송출 절차

기기 1대에 GLOBAL·ORG·REGION·DEVICE 편성이 동시에 걸릴 수 있다. 서버가 요청 시점에 다음 순서로 하나의 목록을 만든다.

3.1서버 — 4단계 합성

SERVER
  1. 후보 선별 — 다음을 모두 통과한 편성만 남긴다
    조건내용
    사용 여부USE_YN = 1
    기간START_DATE ≤ 오늘 ≤ END_DATE (END_DATE 없으면 무기한)
    요일DAYS_OF_WEEK 비트마스크(월~일)에서 오늘 자리가 1
    시간대TIME_START ~ TIME_END 안 (미지정=종일, 자정 넘김 지원)
    스코프GLOBAL(전체) · DEVICE(기기ID) · ORG(단체) · REGION(시도·구군) 중 이 기기에 해당
  2. 우선순위 판정
    방식조건결과
    대체(replace)기본PRIORITY 최댓값 그룹의 항목만 송출, 하위는 전부 무시
    혼합(mix)최상위 그룹에 MIX_RATIO 가 있고 하위 그룹도 존재상·하위 노출량을 비율 : (100-비율) 로 근사해 둘 다 송출

    예) GLOBAL(우선순위 0) + ORG(우선순위 10) → ORG 만 송출.
    ORG 에 MIX_RATIO=70 을 주면 → ORG 70% : GLOBAL 30% 로 섞어 송출.

  3. 항목 조립 승인(APPROVED)되고 사용 중(USE_YN=1)인 콘텐츠만 SEQ 순으로 담는다. 레이아웃은 최상위 그룹 중 SCHEDULE_ID 가 가장 작은 편성의 재생목록 LAYOUT_ID 를 쓴다.
  4. 버전 계산 기여한 편성·재생목록·콘텐츠의 최신 수정시각 + 항목구성 해시 + 공지 시그니처를 합쳐 scheduleVersion 을 만든다. 플레이어는 이 값이 같으면 응답 전체를 버린다.

3.2플레이어 — 재생

PLAYER
  1. 가중 라운드로빈 WEIGHT 기반 smooth WRR(nginx 알고리즘)로 한 사이클 순서를 만들고 무한 순환한다.

    예) A(weight 3) · B(weight 1) → A A B A 순서로 고르게 분산. 같은 weight 면 SEQ 오름차순.

  2. 캐시 완료분만 재생 다운로드가 끝난 항목만 재생하고, 미완료 항목은 건너뛴다. 전 항목이 미완료면 기본 화면(fallback)을 띄운다.
  3. 재생 완료마다 로그 적재 60초 주기 배치 업로드.

5.송출 중에 재생목록이 수정되면

SERVER
  1. PUT /api/signage/playlists/:id/items 트랜잭션 안에서 기존 항목 전체 삭제 후 재생성(새 ITEM_ID 발급) + 재생목록 수정시각 갱신
  2. 모델 훅이 편성 epoch +1 (즉시)
  3. 다음 스케줄 요청 때 scheduleVersion 재계산 항목구성 해시가 달라져 반드시 변경으로 감지된다
PLAYER
  1. 하트비트 응답에서 epoch 변화 감지 (0~120초) → 지터 0~15초 → 스케줄 재조회
  2. scheduleVersion 불일치 → 적용 시작 새 항목 목록을 localStorage 에 저장
  3. 캐시 동기화 로컬에 없는 파일만 순차 다운로드 → MP4 시그니처 검증(실패 시 1회 재시도)
  4. 편성에서 빠진 파일 삭제 + 캐시 상한(10 GB) 정리
  5. 재생 중인 광고가 끝날 때까지 대기 → 끝나면 새 목록으로 교체 중간에 끊지 않는다
  6. 새 목록의 첫 재생 가능 항목부터 송출 끝난 항목의 재생로그는 정상 적재되어 60초 내 업로드
